# Тестирование (весь стек)

## Уровни тестов
1. **Unit** — чистая доменная логика без внешних зависимостей (игровые движки, валидация, парсинг). Без Docker, без моков I/O.
2. **Integration** — сервис + реальная БД/Kafka/Redis, но в изоляции от остальных сервисов. Во время разработки тесты можно запускать локально против выделенного тестового окружения, в том числе с зависимостями через Compose или testcontainers-go. Перед ревью повторить релевантные проверки в Docker.
3. **E2E** — тест идёт через реальный клиентский путь (HTTP/Connect/WebSocket). Промежуточные проверки разрешены против локального dev-запуска; перед ревью обязательна проверка против актуального стека в Docker Compose (gateway + необходимые сервисы и инфраструктура).

## Правило: E2E-тест обязателен на каждую крупную фичу
"Крупная фича" = новый флоу, доступный конечному пользователю (не рефакторинг, не внутренний рефактор пакета). Примеры, что требует e2e:
- Регистрация / логин / OAuth-флоу целиком (клиент → auth → JWT выдан → gateway принимает токен)
- Партия в игру от создания сессии до победы/ничьи для **каждой игры отдельно** (включая Quoridor — полный сценарий с несколькими стенами)
- Отправка/получение сообщения в чате между двумя участниками
- Установка звонка: создание комнаты → выдача токена → участник подключился (можно мокать сам LiveKit медиапоток, но проверять оркестрацию: комнаты/токены/вебхуки)
- Любой новый gRPC/Connect метод, который дергает клиент напрямую

E2E-тест живёт рядом с фичей (`services/<name>/e2e/`). Во время разработки runner может работать локально. Итоговый прогон перед ревью выполняется против Docker-стенда; серверные Go E2E запускать через Compose, браузерный runner и XCUITest могут работать на устройстве.

## Перед передачей на ревью
- Собрать актуальные изменения и поднять Docker-стенд по `.claude/rules/infra.md`.
- Прогнать релевантные тесты; UI проверить живьём в браузере на Docker-стенде по изменённому пользовательскому сценарию. После исправлений повторить успешный путь.
- В результате указать проверенный адрес Docker-стенда и выполненные проверки. Успешного локального dev-запуска недостаточно, чтобы объявить задачу готовой к ревью.

## Инструментарий
- Go: `testcontainers-go` для integration, отдельный `docker-compose.e2e.yml` для полного стека в e2e.
- Web: Playwright — локальный dev-стенд во время разработки, поднятый через Docker стек перед ревью (gateway + fake/реальные сервисы).
- Мобилка/десктоп (SwiftUI): XCUITest — против того же Docker-стека через настраиваемый base URL.

## CI
- Unit — на каждый PR, быстро.
- Integration/E2E — на каждый PR перед мержем в основную ветку (не на каждый коммит в фиче-ветке, чтобы не тормозить итерацию).
