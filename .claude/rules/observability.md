# Observability (весь backend)

## Логи
- Только структурированные (JSON), никаких `fmt.Println`/голого `log.Print` в бизнес-логике — единая обёртка в `shared/pkg/logger`.
- Обязательные поля в каждой записи: `service`, `request_id`/`correlation_id`, `level`, `timestamp`.
- `correlation_id` генерируется на gateway на входе запроса и прокидывается через все downstream-вызовы (gRPC metadata / Kafka headers) — без этого не отследить один запрос через несколько сервисов.
- Уровни: `debug` (только dev), `info` (значимые события — сессия создана, ход сделан), `warn` (восстановимые аномалии), `error` (требует внимания).

## Метрики
- Prometheus-совместимые `/metrics` эндпоинты на каждом сервисе.
- Обязательный базовый набор на сервис: request rate, error rate, latency (p50/p95/p99) по каждому RPC-методу — через middleware, не вручную в каждом хендлере.
- Игровой сервис отдельно: активные сессии по типу игры, среднее время партии — полезно для портфолио-демонстрации (дашборд).

## Трейсинг
- OpenTelemetry — трейсы прокидываются от gateway через все сервисы, которые участвуют в обработке запроса (включая Kafka producer/consumer, где это осмысленно).
- Не обязателен на старте проекта (можно добавить позже), но `correlation_id` в логах закладывать с первого дня — трейсинг потом наложится поверх, а без correlation_id придётся переделывать логирование ретроактивно.

## Health checks
- Каждый сервис отдаёт `/healthz` (liveness — процесс жив) и `/readyz` (readiness — зависимости вроде Postgres/Kafka доступны).
- `docker-compose.yml` — healthcheck на каждый сервис через `/healthz`, зависимые сервисы (`depends_on: condition: service_healthy`) не стартуют раньше, чем их зависимости готовы.
