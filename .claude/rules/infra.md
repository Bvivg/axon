# Инфраструктура (core/deploy)

## Локальная разработка, Docker для ревью
- Полный запуск разработки — `npm run start:dev` из корня репозитория. Команда готовит env, зависимости и миграции, поднимает инфраструктуру и запускает web и все реализованные Go-сервисы напрямую на устройстве. Ctrl+C останавливает локальные процессы, инфраструктура продолжает работать. Не пересобирать Docker-образы на каждой итерации.
- Для отдельного запуска web использовать `npm run dev` из `ui/web`, Go-сервисов — `go run`, SwiftUI — Xcode, когда клиент будет реализован. Настройки полного локального запуска задавать в корневом `.env.local`, порты — через `DEV_*_PORT`; `.local/dev/` содержит только игнорируемые логи и служебные файлы.
- Установку зависимостей проекта, генерацию кода, форматирование, линтеры и промежуточные тесты выполнять локально. Миграции и тесты с побочными эффектами направлять только в выделенное dev/test-окружение.
- Postgres/Redis/Kafka/coturn/LiveKit при необходимости можно держать в Docker как инфраструктурные зависимости локально запущенного приложения. Адреса и порты задавать через env; локальный запуск не должен зависеть от внутренних DNS-имён Compose.
- Сохранять Dockerfile и Compose-конфигурацию рабочими при изменении зависимостей, команд запуска, env и миграций. Новые необходимые runtime-зависимости должны быть воспроизводимы на Docker-стенде.
- Перед передачей пользователю на ревью собрать актуальный код, поднять приложение и его зависимости в Docker Compose, применить необходимые миграции и проверить изменённый сценарий на этом стенде. Локальный dev-запуск не заменяет эту проверку.
- Пользователю давать ссылку только на проверенный Docker-стенд и оставлять его запущенным для ревью. Проверить, что адрес ведёт именно в Docker, а не в локальный dev-процесс; при конфликте портов развести их. Если Docker-проверка заблокирована, сообщить причину и не объявлять результат готовым к ревью.
- Перед управлением Compose проверить `docker compose ls` и каталог проекта; поднимать, пересобирать и перезапускать только стек Axon, не затрагивая другие проекты.

## Сети по зонам ответственности
- Стек Axon — один compose-проект `axon` с сетями по зонам: `edge` (то, что достижимо с входа: TLS-фронт, web, gateway, auth, minio), `app` (вызовы между сервисами), `data` (Postgres/Redis/Kafka/MinIO и джобы миграций), `media` (звонки: LiveKit, coturn, chat, gateway), `lan` (DNS и проверки для доступа с устройств в сети), `obs` (сбор телеметрии: OTel Collector, Prometheus, Tempo, Loki, Alloy, Pyroscope, Grafana; сервисы подключаются к ней только в overlay `docker-compose.observability.yml`).
- Любой новый контейнер или overlay получает явный `networks:` только с теми зонами, которые нужны ему по ответственности; сеть `default` не используется. Новая зона заводится, только если появляется ответственность, которую не покрывает ни одна из существующих.
- Контейнеры Axon создаются только через Compose: никаких `docker run`/`docker network create` из скриптов и руками. Всё, что относится к стенду или локальной разработке, — сервис проекта `axon` (одна группа в Docker Desktop) с сетями своей зоны; вспомогательные dev-контейнеры (например, `livekit-bridge` для локального запуска) — сервисы с `profiles: ["dev"]`, которые `start-dev` поднимает по имени.
- Одноразовые проекты (e2e-прогоны, утилиты вроде graphify) называются `axon-<назначение>` и после прогона убираются `docker compose -p axon-<назначение> down`, чтобы в Docker не оставалось осиротевших групп, контейнеров и сетей.
- Тома, которые объявляет образ (`VOLUME`), но сервису не нужны (секреты Kafka, `/data` Redis без персистентности, `/var/lib/coturn`), закрываются `volumes: - type: tmpfs` (короткий `tmpfs:` не помогает): иначе каждый контейнер оставляет анонимный том. Данные, которые должны жить, — только в именованных томах.
- Bind-mount в overlay, лежащем вне `core/deploy`, задаётся абсолютным путём: относительные пути Compose считает от `--project-directory` (`core/deploy`), а не от файла overlay, и Docker молча создаёт пустой каталог вместо нужного файла.
- Хранилища видят только сервисы-владельцы и джобы: web, TLS-фронт, gateway и медиасервер не подключаются к `data`. Из стека телеметрии к `data` подключён только postgres-exporter.
- Режим отказоустойчивости (три брокера Kafka, `game` ×2) — overlay `docker-compose.ha.yml`, базовый стек — один брокер и один `game`. Тяжёлые режимы добавляются overlay-файлами, а не включаются по умолчанию.
- Тестовые стеки (`docker-compose.e2e.yml`, `docker-compose.web-e2e.yml` и их overlay) — одноразовые проекты одного прогона и остаются одной сетью.

## Postgres
- Одна база, schema-level изоляция: `auth`, `chat`, `game`, `calling` — каждый сервис пишет только в свою схему, никаких cross-schema JOIN из кода сервиса.
- Миграции — по сервису, в `services/<name>/migrations/`, применяются независимо. На Docker-стенд их накатывают одноразовые джобы `<service>-migrate`, сервис стартует только после своей.
- Postgres работает с `wal_level=logical`. Роль `debezium` и публикацию `axon_outbox` (только `INSERT`) создаёт идемпотентный джоб `cdc-setup` после всех `*-migrate`: новая таблица `<schema>.outbox` попадает в публикацию на следующем `up`, если её migrate-джоб добавлен в `depends_on` у `cdc-setup`.

## Redis
- Только кэш/presence/session state — не источник истины. Любые данные в Redis должны быть восстановимы из Postgres/Kafka при потере кэша.

## Kafka
- Событийный контракт — `<domain>.<event>` (`game.started`, `game.finished`, `chat.message`, `call.ended`).
- Consumer-группы — по сервису-потребителю, не шарить одну группу между разными сервисами.
- Сервисы не пишут доменные события в Kafka сами: строка в `<schema>.outbox` в той же транзакции, дальше Debezium (`connect`, Outbox Event Router) кладёт `payload` как есть в топик `aggregatetype`, ключ — `aggregateid`, заголовки `event_type`/`event_id`. Схемы событий — `axon.events.v1` в Apicurio (`registry`). `connect`, `registry` и их джобы (`cdc-connector`, `schema-register`) — только в сети `data`.

## LiveKit
- SFU — отдельный контейнер/под, медиапоток идёт напрямую клиент ↔ LiveKit, никогда не проксируется через gateway.
- Calls — бизнес-модуль внутри Chat, таблицы `chat.call_*`; отдельный `calling` оркестратор не создаётся (ADR-1, решение владельца 2026-11-03, `.claude/plans/calls-hybrid.md`). 1:1 использует native WebRTC/coturn; LiveKit и группы относятся только к Рубежу 2. Пустую зарезервированную схему `calling` не удалять. Будущее выделение сохраняет `axon.calls.v1`/Call ID, меняет только Store/Signaling/MediaProvider adapters.

## Docker / K8s
- `docker-compose.yml` — воспроизводимый стенд для проверки и пользовательского ревью; для локальной разработки можно поднимать только нужные инфраструктурные зависимости. Дополнительные сервисы запускать по необходимости и в пределах разрешённого объёма задачи.
- Секреты — только через env/`.env.local`, никогда не коммитить в репозиторий.
