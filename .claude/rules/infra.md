# Инфраструктура (core/deploy)

## Выполнение команд — только через Docker
- Ничего не запускать локально напрямую (`go run`, `npm run dev`, `air`, локальный Postgres/Redis/Kafka и т.д.) — всё выполняется внутри Docker-контейнеров через `docker-compose`.
- Любой запуск сервиса, миграции, теста с побочными эффектами (БД, сеть) — через `docker compose run <service> ...` или `docker compose exec <service> ...`, не на хост-машине.
- Единственное, что можно гонять локально без Docker — статические проверки без побочных эффектов: `gofmt`, линтеры, unit-тесты на чистых функциях без внешних зависимостей (например, `games/quoridor` домен-логика).
- Если для задачи нужен новый сервис/тул — добавлять его в `docker-compose.yml`, а не устанавливать на хост.

## Postgres
- Одна база, schema-level изоляция: `auth`, `chat`, `game`, `calling` — каждый сервис пишет только в свою схему, никаких cross-schema JOIN из кода сервиса.
- Миграции — по сервису, в `services/<name>/migrations/`, применяются независимо.

## Redis
- Только кэш/presence/session state — не источник истины. Любые данные в Redis должны быть восстановимы из Postgres/Kafka при потере кэша.

## Kafka
- Событийный контракт — `<domain>.<event>` (`game.started`, `game.finished`, `chat.message`, `call.ended`).
- Consumer-группы — по сервису-потребителю, не шарить одну группу между разными сервисами.

## LiveKit
- SFU — отдельный контейнер/под, медиапоток идёт напрямую клиент ↔ LiveKit, никогда не проксируется через gateway.
- `calling` сервис — только оркестрация (токены, комнаты, вебхуки), не медиалогика.

## Docker / K8s
- `docker-compose.yml` — для локальной разработки, поднимает все сервисы + Postgres/Redis/Kafka/LiveKit одной командой.
- Секреты — только через env/`.env.local`, никогда не коммитить в репозиторий.
