# Этап 3 (доменная часть) — движок игр и Tic-Tac-Toe

## Context

Этап 3 по `roadmap.md` — это сервис `game` целиком: движок, сессии, gRPC/WS-сервер,
Kafka, метрики и веб-клиент. Здесь делается только **доменная часть**: модуль
`core/services/game` с `internal/engine` и `internal/games/tictactoe`. Причина
разделения — чистый домен не зависит ни от Docker-стека, ни от proto, поэтому
пишется параллельно с другими задачами и гоняется на хосте (единственное
исключение, разрешённое `rules/infra.md`).

Явно вне объёма и остаётся этапу 3: `session`, `server`, `ws`, proto-контракты,
compose, Dockerfile, CI-матрица образов, любые другие игры.

Задача не в tic-tac-toe — он тривиален и нужен как первый потребитель. Задача в
том, чтобы выбрать представление `State` и `Move`, которое проживёт до шахмат и
Quoridor. Сам интерфейс зафиксирован в `CLAUDE.md` и не меняется:

```go
type Game interface {
    Init(players []PlayerID) State
    ApplyMove(state State, move Move) (State, error)
    ValidMoves(state State, player PlayerID) []Move
    IsTerminal(state State) (bool, *PlayerID)
}
```

Результат этой задачи: `registry.Get("tictactoe")` отдаёт игру, партия играется
до победы и до ничьей чистыми вызовами, состояние переживает JSON-round-trip и
восстанавливается реплеем истории ходов.

## Главное решение: конверт + непрозрачная нагрузка

`State` и `Move` — **конкретные структуры уровня `engine`**, в которых есть
game-agnostic скелет и одно поле с игровой нагрузкой в каноническом JSON:

```go
type State struct {
    Game    Key             `json:"game"`     // ключ реализации, состояние самоописуемо
    Players []PlayerID      `json:"players"`  // роспись мест: индекс места -> игрок
    Turn    int             `json:"turn"`     // чьё место ходит, NoSeat в законченной партии
    Ply     int             `json:"ply"`      // сколько ходов уже применено
    Status  Status          `json:"status"`   // in_progress | win | draw
    Winner  int             `json:"winner"`   // место победителя, NoSeat при ничьей
    Data    json.RawMessage `json:"data"`     // всё, что знает только сама игра
}

type Move struct {
    Player PlayerID        `json:"player"`
    Ply    int             `json:"ply"`   // против какой позиции ход посчитан
    Data   json.RawMessage `json:"data"`
}
```

### Почему конверт, а не одно из очевидных решений

- **Не `any`/интерфейс с приведением типа.** Тогда `session` не может ни
  сохранить, ни прочитать состояние, не зная игру: понадобился бы кодек на игру
  в реестре, а любая ошибка типа всплывала бы в рантайме. Инфраструктура должна
  уметь хранить и отдавать состояние, ничего про игру не зная.
- **Не голый `[]byte` без конверта.** Тогда «чей ход», «партия закончена», «кто
  победил» невозможно узнать, не спросив игру, а значит `session`, gateway и
  клиент вынуждены таскать с собой знание о конкретной игре.
- **Не единая типизированная модель на все игры.** Доска 3x3, 64 клетки с
  рокировкой и взятием на проходе, стены Quoridor между клетками и карты дурака
  не сводятся к одной структуре; попытка — это универсальная модель игры,
  которая ломается на первой же нестандартной.

Конверт разделяет ровно по этой линии: инфраструктура знает то, что одинаково у
всех игр, игра — всё остальное. Проверка того, что линия проведена верно:
добавление шахмат и Quoridor не меняет ни одного поля конверта.

### Как это переживает шахматы и Quoridor

- Шахматы: `Data` = позиция (клетки, права рокировки, поле взятия на проходе,
  счётчик полуходов), `Move.Data` = `{"from":"e2","to":"e4","promotion":"q"}`.
  Ничья по повторению позиций — история внутри `Data`, конверт не трогается.
- Quoridor: `Move.Data` — размеченное объединение,
  `{"kind":"step","row":..,"col":..}` либо `{"kind":"wall","row":..,"col":..,"orientation":"h"}`.
  Два разных вида хода в одной игре — это ровно то, чего не выдержал бы конверт
  с фиксированными полями `from`/`to`.
- Дурак: ходит не по кругу и один игрок ходит несколько раз подряд — поэтому
  `Turn` хранится игрой явно (следующее место выбирает `ApplyMove`), а не
  вычисляется как `(seat+1) % len(players)` на уровне конверта.

### Почему именно JSON

Кодировка зафиксирована в типе (`json.RawMessage`), а не спрятана за кодеком:

- `State` целиком маршалится в один читаемый документ — это `jsonb` в Postgres
  (`game.sessions` кэш, `game.moves.data`), где историю партии можно смотреть и
  запрашивать глазами, а не расшифровывать;
- TS-клиенту нагрузка достаётся как обычный объект, без второго слоя декодирования;
- цена сериализации на ход неинтересна: партии человеческие, а не перебор.

### Как это уезжает в proto

Все поля конверта — скаляры, поэтому контракт не зависит ни от одной игры:

```proto
message GameState {
  string game = 1; repeated string players = 2; int32 turn = 3;
  int32 ply = 4;   string status = 5;           int32 winner = 6;
  bytes data = 7;  // канонический JSON, схема принадлежит игре
}
message GameMove { string player = 1; int32 ply = 2; bytes data = 3; }
```

Новая игра не добавляет ни поля, ни `oneof`, то есть не нарушает additive-only
из `rules/api-contracts.md`. `Status` — строка, а не enum: значения приезжают из
`jsonb` и уезжают в TS, где строковое перечисление читается без словаря.

### Хранение и реплей

Состояние в Postgres не хранится как источник истины: хранится история ходов
(`session_id`, `ply`, `player_id`, `data jsonb`), а состояние — это
`Init(players)` плюс свёртка `ApplyMove` по истории. Отсюда два требования,
которые представление обязано выполнять и которые проверяются тестами: ход
сериализуем целиком и применяется к позиции детерминированно.

`Ply` в `Move` — это не порядковый номер ради порядка, а токен оптимистической
блокировки: ход, посчитанный против устаревшей позиции, отвергается
(`ErrStaleMove`). В играх строго по очереди двойную отправку ловит и проверка
очереди, но в дураке один игрок ходит несколько раз подряд — там проверка
очереди не спасает, а `Ply` спасает.

### Общие правила хода — в одном месте

`engine.Precheck(key, state, move) (seat int, err error)` — первая строка
`ApplyMove` каждой игры. В нём живут правила, одинаковые для всех: состояние
принадлежит этой игре, партия не закончена, игрок за столом, его очередь, ход не
устарел. Вынесено, чтобы правила не разъезжались между реализациями; вызывается
самой игрой, а не обёрткой поверх, чтобы прямой вызов из тестов проверял то же
самое, что вызов через реестр.

### Дырка фиксированного интерфейса: `Init` не возвращает ошибку

`Init(players []PlayerID) State` не может отказать при неправильном составе, а
добавлять метод в интерфейс нельзя. Решение — валидация живёт в реестре, а не в
игре: `Definition` несёт `MinPlayers`/`MaxPlayers`, а `Registry.NewState(key,
players)` проверяет состав (в том числе повторяющегося игрока, который иначе
занял бы два места) и только потом зовёт `Init`. Игра остаётся с ровно четырьмя
методами, взаимозаменяемость через `registry.go` не страдает.

## Затрагиваемые файлы

Новый модуль `core/services/game` (`github.com/bvivg/axon/core/services/game`),
без зависимостей — только stdlib. `core/shared` не подключается: домену он не
нужен, а зависимость ради симметрии тянет за собой pgx, redis и prometheus.

| Файл | Что |
|---|---|
| `core/services/game/go.mod` | модуль, только stdlib |
| `core/services/game/internal/engine/engine.go` | `PlayerID`, `Key`, интерфейс `Game`, `Precheck`, декодеры нагрузки |
| `core/services/game/internal/engine/state.go` | `State`, `Move`, `NewState`, `Advance`, `Finish`, `Outcome`, `Seat` |
| `core/services/game/internal/engine/errors.go` | sentinel-ошибки движка |
| `core/services/game/internal/engine/registry.go` | `Definition`, `Registry`, `NewState` с валидацией состава |
| `core/services/game/internal/games/tictactoe/tictactoe.go` | реализация `Game`, `Key`, `Definition`, `NewMove`, `Cell` |
| `core/services/game/internal/games/tictactoe/board.go` | нагрузка состояния: доска, линии победы |
| `*_test.go` рядом с каждым | table-driven тесты, внешние пакеты `engine_test` / `tictactoe_test` |
| `core/go.work` | `use ./services/game` |
| `Makefile` | строка 14 (`GO_MODULES`) и список модулей в цели `tidy` — больше ничего |

Реестр не заполняется через `init()`: он собирается явно в wiring этапа 3
(`reg.Register(tictactoe.Definition())`), чтобы порядок регистрации не зависел от
порядка импортов и тесты не делили один глобальный реестр.

## Как проверяется

```bash
cd core && go test -race ./services/game/...   # весь домен, без Docker
make lint                                       # golangci-lint в контейнере
cd core && gofmt -l services/game               # пусто
```

Покрытие тестами (table-driven, без моков; в тестах реестра — минимальная
заглушка `Game`, потому что реестру нужен хоть какой-то участник):

- партия до победы и партия до ничьей полными последовательностями ходов;
- отказы: занятая клетка, ход вне доски, ход не в свою очередь, ход после
  терминального состояния, устаревший `Ply`, игрок не за столом, битая нагрузка;
- **`ApplyMove` не мутирует вход** — снимок входного состояния в JSON до и после
  вызова, плюс проверка, что `Data` результата не тот же массив, что на входе;
- реплей: ходы прогоняются через `json.Marshal`/`Unmarshal` (имитация записи в
  Postgres) и применяются к свежему `Init` — итог совпадает с состоянием,
  посчитанным напрямую;
- round-trip `State` через JSON не меняет ни одного поля;
- реестр: дубликат ключа, неизвестный ключ, битые `Definition`, неверный размер
  состава, повторяющийся игрок, сортировка `Keys()`;
- партия целиком через реестр: тип игры нигде не назван, кроме регистрации, —
  это и есть проверка взаимозаменяемости.

Тест на отсутствие мутации проверен «от противного»: временная запись в
`state.Data` внутри `ApplyMove` роняет его, то есть тест ловит именно то, ради
чего написан, а не проходит вхолостую.

## Критерий готовности

`go test -race ./services/game/...` и `make lint` зелёные, партия в tic-tac-toe
играется до победы и до ничьей через `engine.Registry`, а решение по
`State`/`Move` зафиксировано здесь настолько, что этап 3 подключает сессии и
proto, не переоткрывая вопрос представления.
