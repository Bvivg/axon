# Этап 1 — Auth + Gateway + веб-логин

## Context

Этап 0 закрыт: есть `shared/pkg`, Docker-стек, buf и CI, но **ни одного сервиса
и ни одного `.proto`**. Ничего не запускается, кроме Postgres и Redis.

Задача этапа — первый сквозной путь: человек открывает браузер, регистрируется,
логинится, и gateway пускает его на защищённый метод по выданному токену. Это
walking skeleton: после него добавление сервиса становится рутиной, потому что
все неочевидные куски — контракты, генерация, DI, middleware, миграции, e2e в
Docker — уже отлажены на живом примере.

Auth и gateway делаются **вместе**: по отдельности проверить нечего. Auth без
gateway — сервис, к которому никто не ходит; gateway без auth — прокси в пустоту.

Порядок внутри этапа выбран так, чтобы как можно раньше получить работающий
`curl`, а браузерный UI навесить последним.

## 1. Контракты

`core/shared/proto/auth/v1/auth.proto`, пакет `axon.auth.v1`.

| RPC | Назначение |
|---|---|
| `Register` | email + пароль → пара токенов |
| `Login` | email + пароль → пара токенов |
| `RefreshToken` | refresh → новая пара со сменой refresh |
| `Logout` | инвалидация цепочки refresh |
| `GetMe` | профиль по access-токену |
| `StartOAuth` | provider → URL авторизации + `state` |
| `CompleteOAuth` | provider + code + state → пара токенов |

Решения по форме:

- Отдельное сообщение `TokenPair { access_token, refresh_token, expires_in, token_type }`,
  чтобы клиент не гадал про TTL.
- `GetMe` **не принимает** `user_id`: пользователь берётся из токена. Метод,
  принимающий чужой ID, рано или поздно отдаст чужие данные.
- Все новые поля `optional`, номера не переиспользуются (`reserved` при удалении).

Генерация уже настроена: Go уходит в `core/shared/gen/go`, TS — в `ui/web/src/gen`
(`buf.gen.yaml`, managed mode). Проверка — `make proto-lint`, затем `make proto`.

## 2. Сервис `auth`

Новый модуль `core/services/auth` (добавить в `core/go.work` и в `GO_MODULES`
Makefile — сейчас там только `./shared/...`).

```
services/auth/
├── cmd/auth/main.go          # только wiring
├── migrations/
├── .air.toml                 # Dockerfile.service ожидает его в корне модуля
└── internal/
    ├── config/               # Base + специфика auth
    ├── domain/               # User, Credential, RefreshToken, sentinel-ошибки
    ├── repository/           # Postgres, схема auth
    ├── jwt/                  # RS256, JWKS, kid
    ├── password/             # argon2id
    ├── oauth/                # Provider + google/github/apple + fake
    ├── service/              # бизнес-логика, транспорт не знает
    └── server/               # Connect-хендлер, домен-ошибки → connect.Code*
```

### Схема БД (`migrations/0001_init.up.sql`)

| Таблица | Ключевое |
|---|---|
| `users` | `id uuid pk`, `email citext unique`, `email_verified`, timestamps |
| `credentials` | `user_id fk`, `password_hash` — отдельно от `users`, потому что OAuth-пользователь пароля не имеет вовсе |
| `refresh_tokens` | `id`, `user_id`, `token_hash`, `family_id`, `used_at`, `revoked_at`, `expires_at` |
| `oauth_accounts` | `provider`, `provider_user_id`, `user_id`, unique на `(provider, provider_user_id)` |

Сам refresh-токен в БД **не хранится** — только хэш. Утечка дампа не должна давать
возможность войти.

### Пароли

argon2id (`golang.org/x/crypto/argon2`), параметры в конфиге, в хэш пишется строка
с параметрами — иначе их нельзя поднять, не разлогинив всех. Сравнение —
`subtle.ConstantTimeCompare`.

### JWT

- RS256, приватные ключи из env, активный — `JWT_ACTIVE_KEY_ID`.
- **JWKS с первого дня отдаёт множество ключей**, а не один. Ротация: ключ сперва
  появляется в JWKS и только следующим релизом начинает подписывать. Иначе клиенты
  с закэшированным JWKS отвалятся в момент ротации.
- Claims: `sub`, `iss`, `aud`, `exp`, `iat`, `jti`.

### Refresh rotation + reuse detection

Каждое обновление выдаёт новый refresh и помечает старый использованным. Повторное
предъявление использованного токена означает кражу — отзывается **вся цепочка
`family_id`**, а не только предъявленный токен. Обязательный сценарий в тестах.

### OAuth — ✅ ВЫПОЛНЕНО (fake + Google + GitHub + Apple)

`services/auth/internal/oauth/`. Интерфейс `Provider`:
`ID()`, `AuthorizationURL(state, challenge)`, `Exchange(ctx, code, verifier)`.

- **Реестр закрыт по умолчанию.** Провайдер без пары `client_id`/`client_secret`
  в реестр не попадает и даёт `ErrProviderUnsupported`. Наполовину заполненная
  запись считается отсутствующей: иначе провайдер выглядит доступным и падает на
  обмене, посреди чужого входа.
- **`state` одноразовый**, в Redis через `GETDEL` — чтение и удаление одной
  операцией, поэтому два одновременных callback'а не могут пройти оба. В `state`
  лежит и провайдер: выданный для Google не закрывает флоу GitHub.
- **PKCE S256.** Формально мы конфиденциальный клиент, но перехваченный `code`
  без verifier бесполезен.
- **Непроверенный e-mail — отказ.** Аккаунты сопоставляются по адресу, поэтому
  без этой проверки достаточно зарегистрировать `victim@example.com` у ленивого
  провайдера, чтобы забрать чужой аккаунт. Ровно эта проверка делает безопасной
  привязку провайдера к существующему password-аккаунту.
- **GitHub требует двух запросов.** `GET /user` отдаёт `email: null` тем, кто
  скрыл адрес в настройках — это настройка, а не крайний случай. Адрес берётся
  из `GET /user/emails`, только primary и только verified. Идентификатор —
  числовой `id`, никогда не `login`: логины меняются и переиспользуются.
- **Fake-провайдер** гоняет настоящий редирект и настоящий обмен, без третьей
  стороны, и **отказывается запускаться при `APP_ENV=production`** — там это не
  удобство для тестов, а обход аутентификации.
- **`redirect_uri` ведёт на веб-клиент** (`/auth/callback/<provider>`): клиент
  читает `code` из query и зовёт `CompleteOAuth`. Токены не летят через редирект.
- **`return_to` по точному allow-list origin'ов.** Открытый редирект здесь — это
  способ собирать чужие authorization code.

`auth` теперь подключается к Redis (только под `state`) и Redis входит в
`/readyz`.

**Apple — ✅ ВЫПОЛНЕНО** (детали в `auth-apple-signin.md`). Он не влез в общий
`httpProvider` и получил свой тип, как и предполагалось: `client_secret` —
ES256-JWT из `.p8` с ротацией, профиль приходит в `id_token` и проверяется по
JWKS Apple, callback — `form_post`.

`form_post` шлёт **браузер**, поэтому `redirect_uri` обязан быть публично
достижим. Открывать второй браузерный вход на `auth` нельзя — граница доверия
gateway, — так что появился роут на уже публичном веб-origin:
`POST /auth/apple/callback` → 303 на существующую страницу
`/auth/callback/apple?code&state`. Адрес выводится из `OAUTH_REDIRECT_BASE_URL`,
пятой переменной окружения не завелось.

Имя пользователя Apple присылает ровно один раз, при первой авторизации, и
только в теле form_post. Оно едет в `CompleteOAuthRequest.display_name`
(`optional`, добавлено additive-only) и подставляется, только если сам провайдер
имени не дал. Промежуточный вариант — упаковка `base64url(JSON{code,name})` в
поле `code` — снят.

Реальных ключей по-прежнему нет, поэтому в реестр Apple не попадает и ведёт себя
как любой ненастроенный провайдер; всё покрыто unit-тестами с ключом, который
генерируется прямо в тесте.

## 3. Сервис `gateway` — ✅ ВЫПОЛНЕНО

Новый модуль `core/services/gateway`.

- Connect-хендлер отдаёт один контракт как gRPC + gRPC-Web + JSON.
- **JWT проверяется локально** через JWKS с кэшем и фоновым обновлением. Поход в
  auth на каждый запрос — ровно то, чего схема с JWKS должна избежать.
- CORS — явный allow-list из `CORS_ALLOWED_ORIGINS`, `*` недопустим.
- Rate limiting: общий лимит и отдельный жёсткий на `Login`/`Register` — это точки
  для брутфорса.
- Входная валидация (форматы, длины) здесь: gateway — граница доверия.
- correlation_id генерируется на входе и уходит в gRPC-метаданных downstream.

Оба сервиса: `/healthz`, `/readyz`, `/metrics` на отдельном порту (`MetricsAddr`),
не на публичном.

Расхождения с замыслом:

- **Входная валидация осталась в домене `auth`, а не на gateway.** Дублировать
  правила формата email и длины пароля в двух местах — это два места, которые
  разъедутся. Gateway остаётся границей доверия для того, что домену не видно:
  кто звонит (JWT), как часто (rate limit) и откуда (CORS). Когда появятся
  сервисы, которым нужна одинаковая проверка размера тела запроса, она ляжет
  сюда как middleware.
- **Проверка токена вынесена в `shared/pkg/authn`.** Изначально верификатор был
  написан внутри `auth`; gateway'ю понадобился тот же код, и второй экземпляр
  той же логики — гарантированное расхождение при первой же правке.
- **Публичный порт — 18080, админский 19090.** 8080 на машине занят, а высокий
  диапазон здесь и так конвенция (55432/56379).
- **Таблица политик закрыта по умолчанию** (`policy.For` на незнакомый метод
  возвращает «требует токена»): новый RPC, который забыли внести в таблицу,
  ломается заметно, а не открывается молча.

## 4. Web (`ui/web`) — ✅ ВЫПОЛНЕНО (Playwright — шаг 10)

Next.js 16 (App Router) + Tailwind 4 + TanStack Query. Регистрация, вход
паролем, вход через провайдера, профиль. Типы — только сгенерированные.

### Refresh-кука ставится на gateway, а не в вебе

Пункт «refresh в `httpOnly`-cookie» требовал того, чего не было: контракт
возвращает `refresh_token` в теле, и никто его в куку не превращал. Сделано
интерцептором на gateway (`internal/cookie`), а не BFF-роутом Next.js —
gateway уже объявлен границей доверия, его CORS был написан ровно под этот
вариант, и логика живёт один раз для всех клиентов.

Браузер отличается по заголовку `Origin`: браузер обязан слать его на любой
cross-origin POST, а Connect всё возит POST-ом, поэтому скрипт страницы не может
отказаться от куки и получить токен в теле. Клиенты без `Origin` (connect-swift,
e2e-набор) сохраняют прежнее поведение — доказательством служат 24 старых
e2e-сценария, прошедших без единой правки.

Для браузера кука — единственный источник: токен в теле запроса отбрасывается, а
не используется как запасной путь. Атрибуты: `HttpOnly`, `SameSite=Lax`
(порт для SameSite не важен, так что 3000 и 18080 — один сайт),
`Path=/axon.auth.v1.AuthService/`, host-only, `Secure` по умолчанию везде кроме
`APP_ENV=development`. Контракт не менялся: поле осталось на месте и приходит
пустым.

### Клиент

- Два транспорта: `bareTransport` для процедур, которые сессию создают, и
  транспорт с интерцептором для вызовов от имени пользователя. Refresh через
  ретраящий транспорт означал бы, что неудачный refresh вызывает следующий.
- Одна общая in-flight ротация на всех ждущих. Refresh-токены ротируются, и
  предъявление потраченного — это как раз то, чем сервер детектирует кражу:
  десять компонентов, отреагировавших на одну просрочку, отозвали бы все сессии
  пользователя.
- Access-токен — в модульной переменной. Восстановление сессии на загрузке —
  один `RefreshToken` с пустым телом, который наполняет кука.
- `return_to` уходит абсолютным: сервер сверяет его со списком точных origin, а
  у голого пути origin'а нет. Нашлось только в браузере.
- Гонка на callback-странице: restore стартует без куки и может ответить «сессии
  нет» уже после того, как `CompleteOAuth` её создал. Флаг `settled` не даёт
  ответу restore перезаписать состоявшийся вход.

### Запуск

Только через Docker: `core/deploy/Dockerfile.web` с таргетами `dev` и `runtime`,
сервис `web` в `docker-compose.yml`, one-shot команды — через сервис `node` в
`docker-compose.tools.yml` (`make web-lint`/`web-typecheck`/`web-build`).
`src/gen` в `.gitignore`, поэтому `buf generate` обязателен до сборки — и в
образе, и в CI.

Найдено по дороге: джоб `deploy-config` упал бы на первом же прогоне CI —
`docker-compose.yml` объявляет `env_file: .env`, а он git-ignored.

| E2E | Refresh-кука: тела без токена, атрибуты, refresh по одной куке, `Logout` гасит куку и цепочку, тело браузера игнорируется, не-браузер не задет | `services/auth/e2e/cookie_test.go` |
| E2E (браузер) | 6 сценариев в Chromium: регистрация, вход паролем, провайдер целиком, перезагрузка не роняет сессию, токен недостижим из скрипта, выход | `ui/web/e2e/` |

Go-набор e2e — **29 сценариев** (плюс 7 подтестов). Ранее в заметках фигурировала
цифра 31 — это была ошибка счёта.

Разделение уровней: в integration попадает только то, что невидимо ни снизу
(моки не арбитрируют гонку), ни сверху (через HTTP тайминг не воспроизвести).

Ключевые решения:

- **E2E гоняется на `runtime`-образах**, а не на `dev` с air. Зелёный прогон
  против контейнера с hot-reload ничего не говорит про то, что уедет в прод.
- **Порты на хост не публикуются.** Прогон не конфликтует ни с dev-стеком, ни с
  другим прогоном, ни с занятым 8080.
- **`TRUSTED_PROXIES=1` на e2e-gateway.** Весь трафик прогона идёт с одного
  адреса, поэтому каждый тест подставляет свой `X-Forwarded-For` и получает
  собственную корзину лимитера. Побочно покрывается путь `ratelimit.ClientIP`,
  которым gateway пойдёт за ingress.
- **Ключ подписи генерируется на каждый прогон** в `core/deploy/.env.e2e`
  (в `.gitignore`) — в репозитории нет ключа даже тестового.
- **Бинарник умеет `-healthcheck`** (`shared/pkg/health`): в distroless-образе
  нет shell, wget и curl, а healthcheck нужен.

В CI стало семь джобов: формат/vet/unit, линтер, контракты, compose,
integration, e2e (с выгрузкой логов сервисов при падении), сборка
runtime-образов. Найденный по дороге баг: линтер в CI не покрывал `gateway`
вообще.

## 6. Браузерный e2e — ✅ ВЫПОЛНЕНО (шаг 10, закрывает этап)

Шесть сценариев в Chromium внутри сети compose, против **runtime**-образов:
регистрация, вход паролем, вход через fake-провайдера целиком, перезагрузка не
роняет сессию, refresh-токен недостижим из скрипта, выход делает профиль
недоступным. Отдельный `docker-compose.web-e2e.yml`, цель `make test-web-e2e`,
джоб в CI.

### Находка: кука требует общего домена

`SameSite=Lax` резал refresh-куку, потому что `web` и `gateway` — два
несвязанных однословных хоста, то есть **разные сайты**. Chromium сообщает
причину только через CDP; снаружи это выглядит как сломанный код сессии — вход
проходит, перезагрузка разлогинивает.

Отсюда следствие для деплоя, до сих пор бывшее неявным: **веб-клиент и gateway
обязаны делить общий регистрируемый домен в любом окружении.** В dev это
работало случайно — оба на `localhost`. Разнеси их по несвязанным доменам, и
кука молча перестанет ходить. В e2e-стеке восстановлена продовая топология:
`web.axon.test` / `gateway.axon.test` / `auth.axon.test`. Домен `.test`
зарезервирован RFC 6761 и наружу не резолвится; `.dev` непригоден — он в
HSTS-preload, и Chrome принудительно переводит его на HTTPS.

Вторая настройка того же рода: `REFRESH_COOKIE_SECURE=false` в браузерном стеке,
потому что при `APP_ENV=test` кука уходит с `Secure`, а браузер отвергает такие
куки на plaintext-origin, если это не `localhost`.

Обе подтверждены отрицательным контролем, а не рассуждением: откат любой из двух
красит ровно сценарии 4 и 5, тогда как 1–3 остаются зелёными — их несёт
access-токен в памяти. Тот же контроль вскрыл, что сценарий выхода проходил
вхолостую, и теперь он проверяет наличие куки до выхода.

## Верификация

```bash
make up                 # postgres, redis, auth, gateway — все healthy
make proto              # контракты сгенерированы
make check              # gofmt, vet, go test -race
make lint               # golangci-lint, включая e2e/integration за тегами
make test-integration   # testcontainers поднимает Postgres
make test-e2e           # полный стек на runtime-образах, сносится после прогона
make test-web-e2e       # Playwright в Chromium внутри сети compose
make web-check          # lint + typecheck + build веб-клиента
```

Ручная проверка: зарегистрироваться и залогиниться в браузере на
`http://localhost:3000`, увидеть профиль. В логах обоих сервисов на один запрос —
один и тот же `correlation_id`.

## Критерий готовности — ✅ достигнут

В браузере проходит регистрация и вход — паролем и через fake-OAuth, — gateway
пускает по выданному токену на защищённый метод, а e2e-сценарии password и OAuth
зелёные в CI. Сверх исходной формулировки браузерный путь теперь не только
проверен руками, но и закодирован в Playwright-наборе, который гоняется в CI.
