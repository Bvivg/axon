# Фаза 7 — функции, которые показывают архитектуру

## Контекст
Фазы 1–5 построили журнал ходов в Kafka, проектор в Postgres, outbox/CDC с событиями
`game.finished.v1` и рейтинговый сервис. Пользователь пока видит это только как «партия работает».
Фаза 7 добавляет функции, которые без этих решений не сделать дёшево: наблюдение за партией без
влияния на игроков, просмотр любой партии по ходам из журнала, анализ сыгранных партий
асинхронным воркером, турниры как распределённую сагу, нативный клиент на тех же контрактах.

Фаза делится на четыре части, каждая — своя ветка и свой PR; порядок 7a → 7b → 7c → 7d,
7a и 7c не зависят друг от друга.

## 7a — наблюдатели и replay (`feat/game-spectate-replay`)
- **Наблюдатели.** Команда `subscribe` разрешена не только участникам: зритель получает те же
  снапшоты сессии, но любая команда хода/отмены/ничьей от него — `SESSION_ERROR_NOT_PARTICIPANT`.
  Зрители считаются отдельно на владельце партии (`game_spectators` gauge, лимит
  `GAME_SPECTATOR_LIMIT` на партию, по умолчанию 200), число зрителей приходит в снапшоте
  (`Session.spectators`). Смотреть может любой вошедший пользователь любую начатую партию: ссылка —
  UUID, приватных партий в продукте нет. Партия, где второе место ещё свободно, для чужого
  по-прежнему `NotFound` — на этом держится сценарий приглашения по ссылке.
- **Replay.** RPC `GetSessionHistory(session_id)` — ходы из `game.moves` read model (проектор
  уже пишет их) в порядке ply с позицией после каждого хода, которую считает движок
  (`Init` + последовательный `ApplyMove`, pure, `Rules.Frames`; дыра в ply — ошибка, а не
  молча неверная позиция). Сессия и ходы читаются одним снимком (REPEATABLE READ, read-only, с
  реплики). Для живой партии — до последнего проецированного хода. `ListLiveSessions` — 30
  последних идущих партий (частичный индекс `game_sessions_live`). Web: страница партии в режиме просмотра со слайдером по ходам и стрелками ←/→ для
  chess, quoridor, tictactoe; ссылка «Смотреть» в лобби у идущих партий и «Разбор» у
  завершённых.
- Контракт additive: новые поля `optional`, новый RPC в `GameService`, политика gateway.
- Проверка: unit (replay = последовательность `ApplyMove`, зритель не может ходить), e2e Go
  (зритель видит ходы игроков в реальном времени, ход зрителя отклонён, история совпадает с
  партией), Playwright (наблюдатель видит ход, слайдер реплея показывает позицию на ply N).

## 7b — анализ партий Stockfish (`feat/analysis-stockfish`)
- Сервис `analysis` (`core/services/analysis`): consumer group `analysis` на `game.finished.v1`,
  только `game=chess`, берёт ходы через `GetSessionHistory`, гоняет Stockfish (UCI, бинарь в
  образе, глубина/время из env, пул движков с ограничением параллелизма), пишет оценку каждой
  позиции и классификацию хода (лучший / неточность / ошибка / зевок по потере сантипешек) в
  схему `analysis`. Идемпотентность — `processed_events` как в rating, повторная доставка не
  дублирует строк.
- RPC `GetAnalysis(session_id)` через gateway; статус `pending/ready/failed`.
- Web: в реплее шахмат — шкала оценки, график по ходам, пометки ошибок.
- Метрики: очередь (lag consumer group), время анализа, ошибки движка; трейс от события до записи.
- Проверка: unit (классификация по оценкам, парсинг UCI), integration (воркер с реальным
  Stockfish на короткой партии с заранее известным зевком), e2e (партия до мата → анализ ready с
  ошибкой на нужном ходу), Playwright (график и пометка).

## 7c — турниры, сага (`feat/tournament-saga`)
- Сервис `tournament` (`core/services/tournament`, схема `tournament`): швейцарка/олимпийка на
  N игроков. Сага-оркестратор с состояниями `registration → seeding → round(k) → finished`
  и шагами, каждый из которых — команда в другой сервис через outbox/Kafka и ответное событие:
  создание партий раунда в game (`tournament.round_started` → game создаёт сессии
  `tournament_id`), результаты из `game.finished.v1`, итог — `tournament.finished.v1`.
- Компенсации: отмена турнира до старта возвращает регистрации; неявка (игрок не подключился за
  таймаут) — техническое поражение; падение game посреди раунда не ломает сагу — шаги
  идемпотентны, таймауты через таблицу дедлайнов, а не таймеры в памяти.
- RPC: `CreateTournament`, `RegisterForTournament`, `StartTournament`, `GetTournament`,
  `ListTournaments`, `CancelTournament`. Web: список, страница турнира с сеткой и раундами.
- Проверка: unit (паринг, конечный автомат саги, компенсации), integration (сага с реальными
  Kafka/Postgres, повторная доставка, рестарт оркестратора посреди раунда), e2e (8 игроков —
  турнир до победителя), Playwright (сетка обновляется после партии).

## 7d — SwiftUI-клиент (`feat/app-swiftui-client`)
- `ui/app` по `rules/swiftui-app.md`: один multiplatform target iOS + macOS, `Core/Networking`
  (`ConnectClient` на Connect-Swift, `WebSocketClient` на `URLSessionWebSocketTask`,
  `AuthTokenStore` в Keychain), Swift-типы генерируются из `shared/proto` (`buf generate` с
  `connect-swift`), base URL настраивается.
- Фичи: вход/регистрация, лобби, партия в tictactoe/chess/quoridor (рендер состояния, ходы
  через сокет), наблюдение и replay из 7a. Звонки в клиент не входят.
- Проверка: `xcodebuild test` (unit view models), XCUITest против Docker-стека: вход → создание
  партии → ход → второй клиент через API отвечает → клиент видит ход.

## Критерий готовности
Зритель смотрит живую партию, любую партию можно пролистать по ходам, шахматная партия
получает анализ Stockfish, турнир на 8 игроков доходит до победителя, SwiftUI-клиент играет
партию против Docker-стека — и каждое из этого закрыто e2e.
