# Chat — типы сообщений, reply/forward, скрытие чата для одного участника

## Контекст

Этап 2 закрыл текстовый чат: комнаты, история по курсору, сокет, fan-out через
Redis. Пока пользователь работал с навигацией (сайдбар/боттом-бар, см.
`roadmap.md`), он же обозначил следующий виток чата — то, что делает его похожим
на настоящий мессенджер, а не на текстовый MVP:

- разные виды сообщений (текст, войс, вложение, системные);
- reply — ссылка на родительское сообщение;
- пересылка сообщений;
- «удалил чат у себя» не должно означать «удалил у собеседника».

Это план **на будущее**: ничего из него не реализовано в рамках текущей сессии
(там сделана только навигация). Он существует, чтобы решения не принимались на
ходу, когда до этой работы дойдут руки — часть из них меняет схему `messages`,
и переделывать миграцию после того как в базе уже есть данные, дороже, чем
продумать её один раз.

Результатом считается: сообщение может быть текстом, войсом, вложением или
системным событием; у сообщения может быть родитель (reply) и источник
(forward); участник может скрыть комнату у себя, не трогая её для остальных, и
переоткрыть её новым сообщением, не увидев историю, отправленную до скрытия.

## Решения

### Виды сообщений — колонка `kind` плюс `payload jsonb`

`messages.kind` — `text | voice | attachment | system`, ограничено `CHECK`, не
свободной строкой (`rules/go-services.md`: никаких голых строк для сравнения —
на стороне Go это набор типизированных констант, не `string`).

Данные, специфичные для вида, — в `payload jsonb`, а не в отдельных колонках на
каждый вид: `text` не использует `payload` вообще (тело — в существующей
колонке `body`), `voice` кладёт `{duration_ms, url}`, `attachment` —
`{url, filename, mime, size_bytes}`, `system` — `{event, actor_id, target_id}`
для событий вроде «добавил в группу» / «удалил из группы». Отдельная таблица на
каждый вид была бы гарантией схемы ценой JOIN на каждое чтение истории ради
данных, которые никогда не участвуют в фильтрации или сортировке — только
рендерятся.

*Отвергнуто:* enum-тип Postgres. `CHECK` на текстовой колонке достаточен для
четырёх известных значений и не требует миграции типа при добавлении пятого —
enum в Postgres нельзя расширить в той же транзакции, что и остальные изменения.

### Вложения и войс — только когда выбрано хранилище

`payload.url` для `voice`/`attachment` предполагает объектное хранилище,
которого в стеке нет (`rules/infra.md` перечисляет только Postgres, Redis,
Kafka, LiveKit). Это открытый вопрос, а не решение: MinIO в compose — самый
дешёвый путь (S3-совместимый API, тот же образ что и в проде при переходе на
реальный S3), но сам факт добавления сервиса в стек — решение, которое стоит
принять отдельно, а не протащить бонусом в этом плане. До этого момента `kind`
можно завести и тестировать на `text`/`system`; `voice`/`attachment` ждут
хранилище.

### Reply и forward — два независимых nullable-поля, не одно

```sql
reply_to_id       uuid REFERENCES messages(id) ON DELETE SET NULL,
forwarded_from_id uuid REFERENCES messages(id) ON DELETE SET NULL,
```

Разные поля, а не одно «связанное сообщение»: reply — это ответ в текущем
разговоре, forward — копия чужого сообщения в новый контекст, и сообщение
физически может быть и тем и другим одновременно (переслали и тут же ответили
на пересланное). `ON DELETE SET NULL`, не `RESTRICT`: удаления сообщений в
системе пока нет, но когда оно появится, оно не должно спотыкаться о чужой
reply — потерять ссылку на удалённый оригинал честнее, чем запретить удаление.

### Скрытие чата для одного участника — поля на `room_members`, не новая таблица

```sql
hidden_at        timestamptz,      -- NULL = чат виден
cleared_through_seq bigint NOT NULL DEFAULT 0,
```

Не «доп таблица», как было названо в первой формулировке задачи, а два поля на
уже существующей `room_members`: у неё и так один ряд на пару
`(room_id, user_id)`, и городить вторую таблицу с тем же первичным ключом ради
двух колонок — это JOIN там, где хватило бы `WHERE`.

Правила:
- `ListRooms` не возвращает комнаты, где `hidden_at IS NOT NULL`, для вызывающего.
- «Удалить чат у себя» — `UPDATE room_members SET hidden_at = now(),
  cleared_through_seq = <текущий max(seq) комнаты> WHERE room_id = ? AND
  user_id = ?`. Не трогает ряд второго участника — его `hidden_at` как был,
  так и остаётся.
- История (`ListMessages`) для участника со скрытием фильтрует
  `seq > cleared_through_seq` — до этой отметки для него ничего не было.
- Любое новое сообщение **от этого участника** в комнате снимает скрытие
  (`hidden_at = NULL`), но `cleared_through_seq` не двигает: он это сообщение
  отправил, но старые ему по-прежнему не показывают. Сообщение **от другого**
  участника скрытие не снимает — незачем возвращать комнату тому, кто её убрал,
  только потому что кто-то третий написал.

### Direct-комнаты — это не то же самое, что текущие открытые

Текущая модель комнат — открытая: любой залогиненный может войти по id
(`rules/api-contracts.md`, `JoinRoom` не проверяет ничего кроме сессии). Это
осмысленно для «комнаты по ссылке», но не для личной переписки: находишь
контакт через поиск людей → пишешь первое сообщение → должна создаться
приватная комната ровно на двух участников, куда третий не зайдёт, даже узнав
id.

Значит `rooms` получает `kind` (`open | direct`), и `JoinRoom` отказывает для
`direct`. Создание direct-комнаты — не через существующий `CreateRoom` с именем,
а новый путь: «есть ли уже direct-комната с этим user_id» → если да, писать
туда (и она обязана переоткрыться, если была скрыта — см. выше) → если нет,
создать при первой отправке, не раньше. Ровно то, что в задаче названо «после
отправки первого сообщения создаём чат».

### Поиск контактов — отдельная RPC, не часть чата

Чтобы искать «кому написать», чат должен видеть что-то за пределами своей
схемы, а `rules/infra.md` запрещает кросс-schema JOIN из кода сервиса. Значит
это вызов в auth, не запрос к его таблицам напрямую: новая процедура вроде
`AuthService.SearchUsers(query) -> []{id, display_name}` за тем же
gateway-контуром, что и всё остальное.

Это заодно поверхность для перечисления пользователей (кто-то может подбирать
query и собирать список адресов), так что `rules/security.md` в этом месте
особенно строг: точное совпадение по email или display name, не префиксный
LIKE, и отдельный, более тесный rate limit, чем у обычных чтений — та же
логика, что уже применена к `/login` в `guard`.

## Открытые вопросы

- Объектное хранилище для `voice`/`attachment` — MinIO в compose или сразу
  внешний S3-совместимый сервис. Не решено этим планом.
- Системные события (`kind = system`) — какие именно события есть
  (`added_to_group`, `removed_from_group`, ...) зависит от того, появится ли
  групповое членство сверх текущего «любой войдёт по id»; сейчас список пуст.

## Критерий готовности

Не применимо — план не начат. Готовность определится, когда работа будет
запланирована как отдельный этап в `roadmap.md`.
