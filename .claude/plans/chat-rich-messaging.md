# Chat — типы сообщений, reply/forward, скрытие чата для одного участника

## Статус: в реализации

Этот план был написан заранее (см. историю ниже — контекст и решения не
менялись) и теперь реализуется целиком одной сессией: миграция, домен,
репозиторий, сервис, WS-протокол, Connect-контракт, поиск людей в auth, direct-
комнаты, хранилище вложений/войса, веб-клиент, тесты на всех трёх уровнях.
Решения по открытым вопросам (хранилище, кто может слать `system`) — в разделе
«Решения, принятые при реализации» ниже; остальное — как было спроектировано.

## Контекст

Этап 2 закрыл текстовый чат: комнаты, история по курсору, сокет, fan-out через
Redis. Пока пользователь работал с навигацией (сайдбар/боттом-бар, см.
`roadmap.md`), он же обозначил следующий виток чата — то, что делает его похожим
на настоящий мессенджер, а не на текстовый MVP:

- разные виды сообщений (текст, войс, вложение, системные);
- reply — ссылка на родительское сообщение;
- пересылка сообщений;
- «удалил чат у себя» не должно означать «удалил у собеседника».

Результатом считается: сообщение может быть текстом, войсом, вложением или
системным событием; у сообщения может быть родитель (reply) и источник
(forward); участник может скрыть комнату у себя, не трогая её для остальных, и
переоткрыть её новым сообщением, не увидев историю, отправленную до скрытия.

## Решения

### Виды сообщений — колонка `kind` плюс `payload jsonb`

`messages.kind` — `text | voice | attachment | system`, ограничено `CHECK`, не
свободной строкой (`rules/go-services.md`: никаких голых строк для сравнения —
на стороне Go это набор типизированных констант, не `string`).

Данные, специфичные для вида, — в `payload jsonb`, а не в отдельных колонках на
каждый вид: `text` не использует `payload` вообще (тело — в существующей
колонке `body`), `voice` кладёт `{duration_ms, url}`, `attachment` —
`{url, filename, mime, size_bytes}`, `system` — `{event, actor_id, target_id}`
для событий вроде «добавил в группу» / «удалил из группы». Отдельная таблица на
каждый вид была бы гарантией схемы ценой JOIN на каждое чтение истории ради
данных, которые никогда не участвуют в фильтрации или сортировке — только
рендерятся.

*Отвергнуто:* enum-тип Postgres. `CHECK` на текстовой колонке достаточен для
четырёх известных значений и не требует миграции типа при добавлении пятого —
enum в Postgres нельзя расширить в той же транзакции, что и остальные изменения.

### Вложения и войс — MinIO, публичный бакет по образцу аватарок

Открытый вопрос закрыт по факту: MinIO с тех пор как этот план писался уже
попал в стек (аватарки, `core/services/auth/internal/avatar`). Заводить второй
объектный сторедж или спрашивать заново — оверинжиниринг; вложения используют
тот же MinIO-инстанс, отдельный бакет `chat-attachments`, тот же паттерн, что
у аватарок: **публичное чтение** (`mc anonymous set download`), загрузка через
gateway-прокси (`internal/attachmentproxy`, зеркало `avatarproxy`) на chat-
эндпоинт, который сам льёт объект в MinIO и возвращает `{url, filename, mime,
size_bytes}` — то есть готовый `AttachmentPayload`.

*Осознанное упрощение, не забыто:* публичные URL, не presigned. Приватные
вложения по комнатам (presigned GET с проверкой членства на каждый доступ) —
отдельная, более рискованная задача (истечение ссылок, повторная выдача при
пересылке в другую комнату), которая не является тем решением, что было
принято этим планом изначально («какое хранилище» — не «какая модель
доступа»). Для портфолио-демонстрации публичного чтения достаточно; ужесточение
до presigned — будущий, отдельно спланированный шаг, если до него дойдут руки.

Войс — тот же бакет, тот же эндпоинт: `MediaRecorder` в браузере пишет
`audio/webm`, аплоадится как обычное вложение с `mime` начинающимся на
`audio/`, `payload.duration_ms` считается на клиенте по факту записи.

### Reply и forward — два независимых nullable-поля, не одно

```sql
reply_to_id       uuid REFERENCES messages(id) ON DELETE SET NULL,
forwarded_from_id uuid REFERENCES messages(id) ON DELETE SET NULL,
```

Разные поля, а не одно «связанное сообщение»: reply — это ответ в текущем
разговоре, forward — копия чужого сообщения в новый контекст, и сообщение
физически может быть и тем и другим одновременно (переслали и тут же ответили
на пересланное). `ON DELETE SET NULL`, не `RESTRICT`: удаления сообщений в
системе пока нет, но когда оно появится, оно не должно спотыкаться о чужой
reply — потерять ссылку на удалённый оригинал честнее, чем запретить удаление.

### Скрытие чата для одного участника — поля на `room_members`, не новая таблица

```sql
hidden_at        timestamptz,      -- NULL = чат виден
cleared_through_seq bigint NOT NULL DEFAULT 0,
```

Не «доп таблица», как было названо в первой формулировке задачи, а два поля на
уже существующей `room_members`: у неё и так один ряд на пару
`(room_id, user_id)`, и городить вторую таблицу с тем же первичным ключом ради
двух колонок — это JOIN там, где хватило бы `WHERE`.

Правила:
- `ListRooms` не возвращает комнаты, где `hidden_at IS NOT NULL`, для вызывающего.
- «Удалить чат у себя» — `UPDATE room_members SET hidden_at = now(),
  cleared_through_seq = <текущий max(seq) комнаты> WHERE room_id = ? AND
  user_id = ?`. Не трогает ряд второго участника — его `hidden_at` как был,
  так и остаётся.
- История (`ListMessages`) для участника со скрытием фильтрует
  `seq > cleared_through_seq` — до этой отметки для него ничего не было.
- Любое новое сообщение **от этого участника** в комнате снимает скрытие
  (`hidden_at = NULL`), но `cleared_through_seq` не двигает: он это сообщение
  отправил, но старые ему по-прежнему не показывают. Сообщение **от другого**
  участника скрытие не снимает — незачем возвращать комнату тому, кто её убрал,
  только потому что кто-то третий написал.

### Direct-комнаты — это не то же самое, что текущие открытые

Текущая модель комнат — открытая: любой залогиненный может войти по id
(`rules/api-contracts.md`, `JoinRoom` не проверяет ничего кроме сессии). Это
осмысленно для «комнаты по ссылке», но не для личной переписки: находишь
контакт через поиск людей → пишешь первое сообщение → должна создаться
приватная комната ровно на двух участников, куда третий не зайдёт, даже узнав
id.

Значит `rooms` получает `kind` (`open | direct`), и `JoinRoom` отказывает для
`direct`. Создание direct-комнаты — не через существующий `CreateRoom` с именем,
а новый путь: «есть ли уже direct-комната с этим user_id» → если да, писать
туда (и она обязана переоткрыться, если была скрыта — см. выше) → если нет,
создать при первой отправке, не раньше. Ровно то, что в задаче названо «после
отправки первого сообщения создаём чат».

### Поиск контактов — отдельная RPC, не часть чата

Чтобы искать «кому написать», чат должен видеть что-то за пределами своей
схемы, а `rules/infra.md` запрещает кросс-schema JOIN из кода сервиса. Значит
это вызов в auth, не запрос к его таблицам напрямую: новая процедура вроде
`AuthService.SearchUsers(query) -> []{id, display_name}` за тем же
gateway-контуром, что и всё остальное.

Это заодно поверхность для перечисления пользователей (кто-то может подбирать
query и собирать список адресов), так что `rules/security.md` в этом месте
особенно строг: точное совпадение по email или display name, не префиксный
LIKE, и отдельный, более тесный rate limit, чем у обычных чтений — та же
логика, что уже применена к `/login` в `guard`.

### `system` — пишет только сервис, не клиент

Системное сообщение — это событие вроде «добавил в группу», которое должно
быть достоверным (его нельзя подделать). Список событий пока пуст (см.
«Открытые вопросы» ниже), но сама возможность появиться должна быть закрыта от
клиента с первого дня: WS-кадр `"send"` с `kind = "system"` отклоняется
валидацией на сервисном уровне (`ErrSystemKindNotSendable` или аналог) —
`Service` получает отдельный, не проброшенный по сети метод
`AppendSystemEvent(ctx, roomID, event, actorID, targetID)` для будущего
использования, но сейчас его никто не вызывает.

### Direct-комнаты — точный механизм ленивого создания

`rooms.kind = 'direct'` идентифицируется парой участников, а не только id:
`direct_user_min`/`direct_user_max` (uuid, меньший/больший по сравнению) с
частичным уникальным индексом `WHERE kind = 'direct'` — это и есть «уже есть
direct-комната с этим user_id», O(1) по индексу, без скана `room_members`.

Создание — не отдельным вызовом, а внутри отправки первого сообщения:
- WS-кадр `"send"` получает новый необязательный `to_user_id` — ровно один из
  `room_id`/`to_user_id` должен быть указан.
- `Service.SendDirect` ищет direct-комнату по паре (мин/макс); если нашлась —
  шлёт в неё как обычно (это же снимает `hidden_at`, если она была скрыта —
  общее правило выше). Если нет — создаёт комнату и добавляет сообщение в
  **одной транзакции**: гонка двух одновременных первых сообщений (оба
  участника написали друг другу одновременно, комнаты ещё нет) ловится через
  уникальный индекс — при конфликте транзакция не паникует, а перечитывает уже
  созданную конкурентом комнату и дописывает сообщение туда же.
- Connect-RPC `GetDirectRoom(user_id) -> optional Room` — только чтение, не
  создаёт: нужен веб-клиенту, чтобы понять, переходить ли сразу в
  `/chat/{roomId}` или показать экран «новый разговор, ещё не отправлено» без
  реального `room_id`.
- `JoinRoom` для `kind = 'direct'` — отказ (`ErrDirectRoomNotJoinable`, что
  клиенту транслируется как `CodeFailedPrecondition`).
- `Room.peer_user_id` (proto, только для `direct`) — «второй участник
  относительно вызывающего», чтобы клиенту не приходилось сверяться со списком
  участников ради одного имени.

### Контракт (уточнение формы)

`Message` получает не «сырой» `payload jsonb` на проводе, а типизированный
`oneof` — `voice`/`attachment`/`system` (`text` ничего не занимает, тело в
`body`, как и раньше). Это не отменяет решение хранить `payload jsonb` в
Postgres (та часть плана не менялась) — это только про то, что по сети шаблон
пейлоада типизирован, а не отдан клиенту как произвольный JSON: меньше места
для рассинхрона формы между версиями клиентов.

```proto
enum MessageKind { MESSAGE_KIND_UNSPECIFIED = 0; MESSAGE_KIND_TEXT = 1; MESSAGE_KIND_VOICE = 2; MESSAGE_KIND_ATTACHMENT = 3; MESSAGE_KIND_SYSTEM = 4; }
message VoicePayload      { int64 duration_ms = 1; string url = 2; }
message AttachmentPayload { string url = 1; string filename = 2; string mime = 3; int64 size_bytes = 4; }
message SystemPayload     { string event = 1; optional string actor_id = 2; optional string target_id = 3; }
```

Новые RPC на `ChatService`: `HideRoom(room_id)`, `GetDirectRoom(user_id)`.
(Отправка direct-сообщения — не RPC, а WS-кадр `send` с `to_user_id`, см.
выше — так же, как обычная отправка сегодня существует только по сокету.)

Новые RPC на `AuthService`: `SearchUsers(query) -> repeated PublicProfile`
(точное совпадение по email или display name, самого вызывающего из
результатов исключаем) и `GetUsersPublicProfiles(user_ids) ->
repeated PublicProfile` (батч, не по одному) — второй нужен не только для
поиска, но и чтобы вообще показать аватарки участников комнаты: `Member`
(chat) сегодня не несёт ни email, ни `avatar_urls`, и без обращения в auth
чат не может отрисовать, кто есть кто, красиво. `PublicProfile{id,
display_name, avatar_url, avatar_urls}` — без email и ролей, это не
профиль для админки.

## Открытые вопросы

- Системные события (`kind = system`) — какие именно события есть
  (`added_to_group`, `removed_from_group`, ...) зависит от того, появится ли
  групповое членство сверх текущего «любой войдёт по id»; сейчас список пуст,
  реализуется только каркас (см. выше), UI-триггеров для них в этом заходе нет.
- Presigned/приватный доступ к вложениям вместо публичного бакета — см. раздел
  про хранилище; сознательно отложено.

## Критерий готовности

Собеседник находится через поиск людей, первое сообщение ему создаёт direct-
комнату; сообщение можно отправить как текст, вложение или войс; на любое
сообщение можно ответить (reply) или переслать его в другую комнату; участник
может скрыть комнату у себя без следа для собеседника, и она молча
переоткрывается, когда он снова туда пишет. Всё — end-to-end в браузере и
подтверждено e2e (`core/services/chat/e2e`, `ui/web/e2e`).
