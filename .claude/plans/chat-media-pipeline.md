# Chat — медиа v2: загрузка частями, обработка в фоне, дедуп (срез 3 переноса из nod)

Общий план: `chat-port-from-nod.md`.

## Контекст

Сейчас вложение уходит одним `PUT` до 100 МБ, обрабатывается прямо в запросе
(видео — минуты под открытым соединением), обрыв сети — загрузка заново с нуля.
Один и тот же файл, отправленный дважды, дважды перекодируется и дважды лежит в
MinIO. Брошенные черновики живут до уборщика (24 ч), клиент их не убирает.

Результат: файл до 200 МБ грузится частями по 10 МБ с докачкой, обработка идёт в
фоне со статусом, тот же исходник второй раз не обрабатывается, тот же итог не
хранится дважды; клиент сам удаляет черновики; видео жмётся экономнее, текстовые
документы — brotli.

## Решения

### Сессии загрузки (новое) и готовые загрузки (как было)
- `uploads` остаётся «готовой загрузкой» (kind + payload), сообщение по-прежнему
  ссылается на `upload_id` — поток отправки и пересылки не меняется.
- Новая `upload_sessions`: кто, режим (`media`/`file`/`voice`), имя, размер,
  размер части, число частей, ключ в MinIO (`staging/<id>`), id multipart-загрузки,
  статус `uploading → processing → ready | failed`, причина отказа, итоговый
  `upload_id`, `claimed_at` (взял воркер).
- HTTP (не Connect: тело — байты части), через gateway как нынешняя загрузка:
  - `POST /internal/uploads` `{as, name, size}` → сессия, `part_size`, `part_count`;
  - `PUT /internal/uploads/{id}/parts/{n}` — часть (≤ `part_size`, последняя — остаток);
    повтор той же части перезаписывает её;
  - `GET /internal/uploads/{id}?wait=1` — статус, загруженные части (истина —
    `ListObjectParts` MinIO) и, когда готово, `{upload_id, kind, payload}`;
    с `wait` держит запрос до смены статуса, но не дольше 25 с (без опроса раз
    в секунду — лимит загрузок 60/мин);
  - `POST /internal/uploads/{id}/complete` — сверка частей по MinIO, сборка,
    статус `processing`, задача воркеру; `202`;
  - `DELETE /internal/uploads/{id}` — черновик: прерывает multipart/удаляет
    временный объект; готовую загрузку удаляет, если её не взяло ни одно сообщение
    (иначе `409`).
- Лимит 200 МБ — `CHAT_MAX_UPLOAD_MB`, часть — 10 МБ (`CHAT_UPLOAD_PART_MB`, ≥ 5:
  минимум S3), голос — как было, 10 МБ.

### Обработка в фоне
- Очередь в процессе, воркеров `CHAT_MEDIA_WORKERS` (по умолчанию 1); задачу берёт
  тот, кто проставил `claimed_at` (`UPDATE … WHERE claimed_at IS NULL OR claimed_at <
  now() - 10 min`), поэтому после рестарта зависшие сессии подбираются заново, а
  два экземпляра не обрабатывают одно и то же.
- Воркер скачивает собранный объект во временный файл, считает `sha256` исходника.
  Есть `file_sources (mode, source_sha256) → file_id` — обработки нет, берётся
  готовый файл. Нет — прежний конвейер (`attachment.Pipeline`), `sha256` итога;
  есть `files (kind, sha256)` — новые объекты удаляются, берётся старый файл.
- `files`: id, kind, sha256, payload, ключи объектов, размер, `linked_at`. У
  `uploads` — `file_id` (у старых — пусто). Ссылка на файл в той же транзакции
  обновляет `linked_at`.
- Видео — как в nod: H.264 CRF 25 `medium`, ≤ 1080p, ≤ 30 к/с, `maxrate 4M`, AAC
  128k; уже совместимый H.264/AAC ≤ 4,5 Мбит/с ≤ 1080p — только перепаковка с
  `+faststart`.
- Документы — brotli (q9), если проба первого 1 МБ ужимается ≥ 10 %; объект с
  `Content-Encoding: br`, браузер разжимает сам. Картинки — как сейчас (JPEG/PNG
  ≤ 2560, без метаданных): кодировщика WebP без cgo/wasm в Go нет, выигрыш не стоит
  новой зависимости.

### Уборка
- Сессии `uploading`/`failed` старше 24 ч — прерывание multipart, удаление
  временного объекта и строки; `processing` дольше часа — `failed`.
- Брошенные загрузки — как было, но объекты удаляются только у старых загрузок без
  `file_id`; файлы без загрузок, не привязанные больше часа, — удаляются вместе с
  объектами (повторная проверка условия в том же `DELETE`).

### Веб
- Загрузка частями с прогрессом по байтам, 3 повтора части с паузой, докачка после
  обрыва (по списку частей из `GET`), отмена — `DELETE`.
- Статус чипа: прогресс → «Processing…» → готово; ошибка — текстом у чипа, чип снимается.
- Черновики удаляются при снятии вложения, уходе из чата и закрытии вкладки
  (`pagehide` + `fetch keepalive`). «Удержание» на время отправки из nod не нужно:
  чип снимается из списка в том же обработчике, что шлёт сообщение, а гонку «удалили
  ↔ сообщение уже ссылается» сервер решает сам (`DeleteDraftUpload` под `FOR UPDATE`,
  у отправленного — `409`).
- HEIC → JPEG на клиенте (`heic2any`), большие PNG/JPEG (> 1,5 МБ) — ресайз до
  2560 и WebP/JPEG на клиенте (меньше трафика; сервер всё равно пережимает).

### Расхождения с замыслом (по ходу)
- Документы (`file`) не дедуплицируются: MinIO отдаёт объект напрямую, и имя в
  `Content-Disposition` привязано к объекту — у второго отправителя скачивался бы
  файл с чужим именем. Дедуп — для фото, видео и голоса.
- «Ждать статус» — long-poll по базе (раз в 400 мс внутри запроса, до 25 с), а не
  WS-событие: без новой подписки на сигналы, и работает при нескольких экземплярах.
- Удаление черновика при закрытии вкладки — `fetch(..., { keepalive: true })`: у
  axios нет `keepalive`; остальные вызовы сессий — через axios, как прежний upload.
- Части считает отдельный лимитер gateway (`RATE_LIMIT_UPLOAD_PARTS_PER_MINUTE`,
  600/мин), управляющие запросы — прежний лимитер загрузок; CORS разрешает `PUT`/`DELETE`.
- `MEDIA_TIMEOUT` по умолчанию 15 мин: обработка больше не держит HTTP-запрос.
- Старый `POST /api/attachment` оставлен (контракт additive-only), веб на него не ходит.

## Проверка
- Go unit: части/сверка, выбор remux vs перекодирование, brotli-проба, дедуп.
- Integration (MinIO + Postgres): сессия → части вразнобой → complete → ready;
  повтор того же исходника — без обработки, тот же `file_id`; уборка файлов.
- Core e2e: загрузка 25 МБ тремя частями через gateway, обрыв и докачка, отправка.
- Web e2e: файл частями с прогрессом, отмена, снятие черновика удаляет сессию.
- Живьём: видео 150 МБ, закрытие вкладки во время загрузки — строки нет.

## Критерий готовности
Файл до 200 МБ доходит частями с докачкой, обработка не держит запрос, повторы не
обрабатываются и не хранятся дважды, черновики не копятся; все тесты зелёные.
