# Auth — редактируемый профиль (аватар, имя) и вкладка сессий/устройств

## Контекст

Профиль сейчас — карточка на чтение: email, статус верификации, id, кнопка
выхода. Пользователь попросил вкладки: **«Мой профиль»** (email, имя, фамилия,
опционально никнейм, аватарка — в первую очередь берём из OAuth-провайдеров) и
**«Сессии/входы/устройства»** (список активных входов, разлогинить конкретное
устройство). Аватарку — в 3-4 размерах (маленький/средний/большой/оригинал).

Это реальная работа, не косметика поверх текущей схемы: `users` не хранит имя
и фамилию отдельно, RPC на изменение профиля не существует вообще,
`refresh_tokens` не хранит ничего про устройство/IP (только `family_id`,
`token_hash`, метки времени), а объектного хранилища в проекте нет вовсе —
тот же открытый вопрос, что уже был отмечен в `chat-rich-messaging.md` для
вложений в чате. Он решается здесь, один раз на оба потребителя.

Результатом считается: в «Моём профиле» можно поменять email/имя/фамилию/
никнейм и загрузить аватарку, которая хранится в четырёх размерах; при входе
через Google/GitHub аватар подтягивается автоматически, если пользователь не
загружал свой; во вкладке сессий видно каждый активный вход (браузер/устройство,
IP, когда начат), текущий отмечен, любой можно завершить по отдельности — не
только «выйти везде».

## Решения

### Имя — новые поля, `display_name` не трогаем

`users` получает `first_name`, `last_name`, `nickname` — все `text NOT NULL
DEFAULT ''`, независимые от существующего `display_name`. Не переиспользуем
`display_name` как «вычисляемое из имени/фамилии/никнейма» — его уже читает
чат при снятии join-time снапшота участника (`room_members.display_name`) и
Apple-флоу пишет в него напрямую при первом входе; трогать семантику поля,
которое уже кому-то принадлежит, ломает рефакторингом две вещи ради одной
новой. `UpdateProfile` пишет в `display_name` то же, что вычислила бы логика
показа (`nickname` → `"first_name last_name"` → email до `@`), так что новые
и старые потребители видят одно и то же имя, не заметив разницы в источнике.

Никнейм — косметический, без уникальности: `rules/security.md` не просит
делать его хендлом, а уникальность — это отдельная UX-задача (что показывать
при коллизии), которую пользователь не просил решать сейчас.

### Email — смена сбрасывает `email_verified`

Смена email на `UpdateProfile` — `email_verified = false` сразу же, без
дополнительного шага. Настоящей отправки писем-верификации в проекте пока нет
вообще (флаг существует, но ничего его не выставляет в `true` кроме
провайдера, подтвердившего почту сам); чинить это — отдельная, незапрошенная
задача. Не сбрасывать флаг было бы хуже: непроверенный адрес продолжал бы
выглядеть проверенным.

### Аватар — MinIO, три производных размера плюс оригинал

Объектное хранилище — `MinIO` в compose, S3-совместимый API. Тот же выбор, что
уже был предложен (не решён) в `chat-rich-messaging.md` для вложений/войсов —
здесь он принимается, и оба потребителя получают одну инфраструктуру вместо
двух. `minio-go` — тот же клиент, что говорит с настоящим S3, так что переезд
на прод-хранилище (если он когда-нибудь понадобится) не меняет код, только
конфиг — та же логика, что уже применена к Kafka (`confluent-local` в dev,
Kafka-совместимый брокер в проде).

Размеры — конкретные пиксели, не «примерно»:

| Имя | Сторона | Где используется |
|---|---|---|
| `small` | 48px | сайдбар, список участников комнаты |
| `medium` | 128px | карточка профиля |
| `large` | 512px | полный просмотр профиля |
| `original` | как загружено, потолок 2048px | источник для будущих размеров |

Ресайз — синхронно в хендлере загрузки, не через Kafka: картинка маленькая,
операция — доли секунды, а асинхронный пайплайн ради этого добавил бы
сложность (отслеживание готовности, промежуточное состояние «аватар
обрабатывается») без выигрыша. `disintegration/imaging` — типизированный
ресайз с нормальными фильтрами и учётом EXIF-ориентации, не голый
`golang.org/x/image/draw` вручную.

Бакет `avatars`, ключи `<user_id>/<size>.jpg`, публичное чтение (аватар — не
секрет; presigned URL с истечением добавил бы сложность там, где она не нужна).
Загрузка ограничена по размеру (5 МиБ) и декодируется через `image.Decode` —
что не декодируется как картинка, отклоняется до того, как долетит до диска.

*Отвергнуто:* presigned upload напрямую в MinIO из браузера. Быстрее для
сервера, но добавляет CORS-конфигурацию на MinIO и второй путь ошибок
(браузер ↔ MinIO напрямую, в обход gateway) ради экономии одного прохода байт
через сервис — не оправдано для картинки размером в мегабайты, не гигабайты.

### Аватар из провайдера — только если не загружен свой

`users` получает `avatar_is_custom boolean NOT NULL DEFAULT false`. При
успешном `CompleteOAuth` через Google/GitHub (у них есть `AvatarURL` в
`domain.ProviderProfile`, у Apple и fake — нет) сервис лучшим усилием
скачивает аватар и прогоняет через тот же ресайз-путь, **если**
`avatar_is_custom = false`. Пользователь, один раз загрузивший свой аватар
вручную (`avatar_is_custom` становится `true`), больше не переписывается
провайдером при следующих входах — иначе «сначала берём из провайдеров» тихо
откатывало бы то, что человек только что сам выбрал.

Сбой скачивания/ресайза аватара из провайдера не должен ронять вход:
best-effort, ошибка — в лог, не пользователю.

### Прото — новые поля вместо переиспользования `avatar_url`

`avatar_url` (строка) в `User` остаётся как есть — `rules/api-contracts.md`
запрещает breaking rename. Добавляется `AvatarURLs { small, medium, large,
original }` новым полем `optional AvatarURLs avatar_urls = N`; `avatar_url`
после этой работы зеркалит `medium` для тех, кто ещё не обновился на новое
поле. `first_name`, `last_name`, `nickname` — новые `optional string` на
`User`, по одному номеру поля на каждое, ничего не переиспользуется.

Новая RPC: `UpdateProfile(email?, first_name?, last_name?, nickname?) → User`.
Каждое поле `optional` — отправлено означает «поменять», не отправлено —
«оставить как есть». Загрузка аватара — не через эту RPC (Connect передаёт
JSON/protobuf, не файлы): отдельный HTTP-эндпоинт на auth,
`POST /internal/avatar` за тем же JWT-guard, что и остальной API, проксируемый
через gateway как обычный HTTP, не Connect-процедура.

### Сессии — `family_id` уже был сессией, просто его не было видно

`RevokeFamily(family_id)` уже существует в репозитории и ничего не пишет
заново — просто наконец получает RPC-обёртку: `RevokeSession(session_id)`,
где `session_id` — это и есть `family_id`, просто названный тем именем, каким
его увидит пользователь.

`ListSessions` — новый запрос: одна строка на `family_id` с ещё не истёкшим и
не отозванным токеном, `issued_at` самого раннего токена в цепочке (когда
начат вход), `user_agent`/`ip` последнего токена (устройство, если с него
переподключались через `RefreshToken` — те же значения, потому что записываются
при каждой выдаче, включая ротацию).

`refresh_tokens` получает `user_agent text NOT NULL DEFAULT ''` и
`ip text NOT NULL DEFAULT ''`, заполняемые при каждом `CreateRefreshToken` —
на `Login`/`Register` (новый вход) и на `RotateRefreshToken` (обновление в
рамках существующего). Источник — gateway: `User-Agent` доходит от браузера
как обычный заголовок; IP — то же значение, что уже резолвит
`guard.ClientIPMiddleware` для rate-limit (`TRUSTED_PROXIES`), передаётся на
внутренний хоп явным заголовком, той же схемой, что уже используется для
`Authorization: Bearer` на WS-хопе к chat — auth не обязан доверять
`X-Forwarded-For` от кого попало, только от собственного gateway.

«Текущая» сессия — новый claim в access-токене, `fid` (family id), рядом с
уже существующими `sub`/`jti`/`iat`/`exp`. `ListSessions` сравнивает `fid` из
токена вызова с `family_id` каждой строки — без этого «это устройство»
пришлось бы угадывать по совпадению user-agent, что ненадёжно (два входа с
одного браузера неотличимы).

*Отвергнуто:* хранить готовую метку устройства («Chrome on macOS») в БД.
Парсинг user-agent меняется быстрее, чем хочется мигрировать колонку — сырой
`user_agent` хранится, разбор в читаемую метку — на чтении (веб), не на записи.

## Файлы

| Что | Где |
|---|---|
| Миграция | `core/services/auth/migrations/000002_profile_and_sessions.{up,down}.sql` |
| Контракт | `core/shared/proto/axon/auth/v1/auth.proto` — `AvatarURLs`, поля на `User`, `UpdateProfile`, `ListSessions`, `RevokeSession` |
| Домен | `core/services/auth/internal/domain/user.go` (поля), `token.go` (`UserAgent`, `IP` на `RefreshToken`, `fid` в JWT claims) |

| Gateway | `core/services/gateway/internal/proxy/auth.go` — проброс `User-Agent`/resolved-IP на внутренний хоп; новый HTTP-путь для upload аватара |

| Web | `app/(app)/profile/` — вкладки (`ProfileTab`, `SessionsTab`), форма редактирования, загрузка аватара, список сессий с кнопкой «завершить» |

## Проверка

```bash
make proto                          # AvatarURLs, UpdateProfile, ListSessions, RevokeSession сгенерированы
make check && make lint             # включая новый пакет avatar
make test-integration               # MinIO — testcontainers, как Postgres/Redis/Kafka
make test-e2e                       # смена профиля, загрузка аватара трёх размеров, список сессий, revoke одной не трогает остальные
make test-web-e2e                   # вкладки, форма, аватар, список сессий в браузере
```

## Критерий готовности

Пользователь меняет имя/фамилию/никнейм и видит их сразу; загруженная
аватарка отдаётся в трёх размерах плюс оригинал; вход через Google/GitHub
подтягивает аватар из провайдера, пока пользователь не загрузил свой; вкладка
сессий показывает каждый активный вход с устройством и IP, текущий отмечен, и
завершение одной сессии не трогает остальные.
