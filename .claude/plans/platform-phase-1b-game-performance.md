# Фаза 1b — производительность event-sourced game

## Контекст
A/B после фазы 1 (20 000 матчей, 300 одновременно): 803 → 1524 хода/с, p50 277 → 77 мс.
Это ×1,9, а не обещанные ×3–5. Профиль: game тратит 4,5 ядра, проектор отстаёт на 167 с после пика.
Причины:
- каждое событие хода несёт полный снимок партии и `state_before`. Для шахмат состояние растёт
  с каждым ходом (история SAN/позиций), поэтому JSON-кодирование, Kafka, проектор и Postgres
  платят O(n) на ход, O(n²) за партию; `game.moves.state_before` хранит то же O(n²) на диске;
- проектор открывает транзакцию на каждую партицию каждого poll, пишет `game.sessions` на каждый
  ход, коммитит синхронно и шлёт `pg_notify` на каждую изменённую партию;
- владелец держит в памяти `StateBefore` всех ходов партии;
- зомби-владелец (потерял группу, но не знает об этом) может подтверждать ходы до таймаута сессии.

Результат: ход в журнале — только факт, проектор пишет пачками, у владения есть lease с
самоостановкой. Замер до/после на одной топологии с ядрами на 1000 ходов/с.

## Решение
- **Ход в журнале — факт, а не снимок.** `MoveApplied` несёт ply, данные хода и короткий итог
  (`MoveOutcome`: статус, очередь, остаток часов). Остальные факты (создание, вход, ничья, отмена
  хода, сдача, таймаут, отмена, правка часов) редкие и по-прежнему несут полный снимок.
  Состояние после хода восстанавливается детерминированным повтором правил: `session.Rules.Redo`
  использует тот же код, что и `Rules.Move`. `journal.Fold` применяет событие к базе по ревизии:
  ревизия ≤ базы — пропуск, ровно +1 — повтор, больше — `ErrGap`; итог сверяется с `MoveOutcome`
  (`ErrDiverged`). Старые записи со снимком читаются как раньше.
- **База для повтора — read model.** Проектор пишет состояние и offset одной транзакцией, поэтому
  строка `game.sessions` согласована с `next_offset`; повтор поверх более новой строки безопасен
  благодаря проверке ревизии. Отдельные снимки в журнале не нужны.
- **Время владельца без монотонной части и с точностью до микросекунды**, иначе повтор часов
  мог бы разойтись с оригиналом на миллисекунду.
- **Пакетный проектор.** Один poll — одна транзакция на все партиции с `SET LOCAL
  synchronous_commit = off` (журнал — источник истины, offset в той же транзакции, поэтому потеря
  последних коммитов при падении Postgres лечится повтором). Кэш состояний партий в памяти
  проектора; `game.sessions` пишется один раз на партию за пачку, ходы — одним
  `INSERT … SELECT unnest(…)`; `state_before` больше не пишется (отмена хода берёт его из памяти
  владельца или повторяет партию из `game.moves`). `pg_notify` — только для редких фактов и
  завершения партии (рейтинг), не на каждый ход.
- **Владелец держит в памяти историю только последних ходов** (для отмены хода).
- **Producer:** lz4 и linger 1 мс, идемпотентность остаётся.
- **Quoridor без map.** Профиль под нагрузкой показал, что 42% CPU game уходит не в журнал,
  а в `quoridor.View → LegalMoves`: на каждый показ доски 128 кандидатов-стен × 2 BFS по
  `map[Wall]bool` с копированием map. Стены — две битовые маски `uint64` (8×8 якорей), BFS без
  аллокаций, а полный BFS запускается только для стен, которые перерезают текущий кратчайший
  путь одного из игроков (остальные пути не ломают). `LegalMoves` 597 → 31 мкс, аллокаций
  8613 → 142; property-тест сверяет результат с полным перебором на случайных партиях.
- **Lease с самоостановкой.** `game.owners.lease_until` (время Postgres). Claim ждёт истечения
  lease прежнего владельца и только потом пишет маркер; владелец продлевает lease каждые TTL/3
  одним UPDATE на все свои партиции, не принимает запись после локального дедлайна
  (`начало продления + TTL − запас`) и сдаёт партицию, если продление не удалось. При штатной
  сдаче lease освобождается сразу. TTL 6 с меньше таймаута группы 10 с, поэтому при падении узла
  ожидания нет.

## Файлы
- `core/shared/proto/axon/game/v1/journal.proto` — `MoveOutcome`, поле `outcome` в `MoveApplied`.
- `core/services/game/internal/session/domain.go` — `Rules.Redo`, общий код с `Rules.Move`.
- `core/services/game/internal/journal/{journal,codec,fold}.go` — компактное событие, `Fold`.
- `core/services/game/internal/owner/owner.go` — claim поверх read model, lease, обрезка истории.
- `core/services/game/internal/projection/postgres.go` — пакетная запись, кэш, `synchronous_commit`.
- `core/services/game/internal/cluster/cluster.go` — один `Apply` на poll, сброс кэша при ребалансе.
- `core/services/game/migrations/000006_owner_lease.{up,down}.sql` — `lease_until`.
- `core/services/game/cmd/game/main.go` — `GAME_LEASE_TTL`, linger/lz4.
- `core/services/game/internal/games/quoridor/{board,pathfinding,rules,quoridor}.go` — битовые
  маски стен, `cuts` (стены, перерезающие кратчайший путь).
- Тесты: `journal/fold_test.go` (случайные партии трёх игр: повтор = оригинал байт в байт),
  `owner` (lease: зомби отказывает после дедлайна, claim ждёт чужой lease), projection integration.

## Как проверяется
- `go test -race ./...` в game, `golangci-lint run`, integration (testcontainers) game.
- A/B на стенде (1 брокер, 1 game, `GAME_TEST_HOOKS=true` на время замера): `cmd/loadgen`
  10 000 матчей трёх игр, 300 одновременно, один seed — образ фазы 1 против образа 1b;
  ходы/с, p50/p95/p99, CPU game/kafka/postgres по `docker stats`, ядра на 1000 ходов/с,
  отставание проектора после пика, сверка read model с числом ходов нагрузчика.
- Web e2e chess/quoridor/tic-tac-toe на Docker web-e2e стеке.

## Результаты (2026-11-20)
Стенд: 1 брокер, 1 game, 10 ядер Docker; `cmd/loadgen`, 6000 матчей трёх игр, 1000
одновременно, пауза 260 мс между ходами, seed 11 (скрипт и CSV — `.local/evidence/journal-perf-2026-11-20`).

| | фаза 1 | 1b |
|---|---|---|
| ходов/с | 3498 | 3683 (потолок паузы клиента ~3800) |
| задержка хода p50 / p95 / p99 | 23 / 184 / 335 мс | 2 / 8 / 19 мс |
| CPU game | 4,10 ядра | 2,12 ядра |
| ядер game на 1000 ходов/с | 1,17 | 0,58 |
| отставание проектора после пика | 10 с | 1 с |
| сверка read model | 204 840 = 204 840 | 204 840 = 204 840 |

- Без оптимизации Quoridor 1b тратил столько же CPU, сколько фаза 1 (1,51 против 1,28 ядра
  на 1000 ходов/с): сэкономленное на снимках съедал повтор хода в проекторе (~4% профиля),
  а доминировал `LegalMoves`. Поэтому профиль и правка Quoridor вошли в эту фазу.
- linger 0 против 1 мс: p99 380 против 426 мс, но CPU game +10%; оставлен 1 мс.

## Критерий готовности
На той же топологии фаза 1b даёт заметно больше ходов/с на ядро, чем фаза 1, read model
совпадает с нагрузчиком, а зомби-владелец не подтверждает ходы после истечения lease.
